# 把厚 SKILL.md 拆薄（功能拆分 + 实操流程）

> 合并自原 05-functional-splitting.md + skill-thinning-workflow.md（2026-08-06 去重）。
> 总入口化原则见 `01-core-principles.md` §5——**SKILL.md 只写「这是什么 + 什么时候用 + 怎么用（速记）+ 引用表」，详细内容能拆就拆**。

## 什么时候用

- 要精简某个厚 skill（>95 行，或 SKILL.md 里内嵌了详细说明）
- 刚做了减法但不确定流程对不对
- 判断标准：**主场景高频内容留 SKILL.md（每次都要读的），子场景细节拆 references/（用到才读的）**；数据索引/题库/导视表不算内容，保留

## 触发信号

| 信号 | 判断 |
|:-----|:------|
| SKILL.md > 95 行 | 过了能一口读完的阈值（200 行必拆） |
| 同一章节反复被用户纠正/追加 | 规则在长，结构却没变 |
| 「这技能到底干什么的」说不清 | 丧失了单一职责 |
| 加载一次 token 开销大 | 大部分内容当前场景用不上 |

### 先量三个尺度，再决定动不动手（2026-09-26 实测）

> 起因：`bin/mdcheck` 对一个 **7,628 字符** 的 SKILL.md 报「**15.4KB** ⚠️ 考虑拆」——它报的是**字节数**，中文一个字三字节，换算过去只有 7.6K 字符、99 行。差点为一行提示去拆一个本来不肥的文件。

| 尺度 | 怎么读 |
|:--|:--|
| **字节**（mdcheck／`ls`） | 中文文件 **÷3 ≈ 字符感**。**别拿它当拆薄触发** |
| **字符**（`len(text)`） | 真正的「内容量」。< 15K 字符基本没什么好拆的 |
| **行数** | 阈值判据（>95 预警／200 必拆）用的就是它 |

**顺序**：量三尺度 → 查 GROUP 分类 → 再决定。**D 类（资料库型）不硬减**——给 D 类动刀，拆出来的 references 会比 SKILL 本身还零碎（实测：`short-stories-liya` 去重只得 −3.4%，而 B/C 类同类操作普遍 −60% 以上）。

**最低风险的减法 = 去重**：同一份信息写两遍的（枚举／清单／指向），删一处留指针、另一处指向原件。删完 **`grep` 抽查**「删掉的东西在原件里是否还在」——这是减法版的守恒校验。

## 拆分公式

```
1 × 厚 SKILL.md → 1 × 薄索引 SKILL.md + N × 功能文件(.md) + 已有 references/ + scripts/
```

## 实操流程

```text
① 读原 SKILL.md        → 摸清有什么章节
② 功能审计             → 按「打开这个文件是为了做哪件事」分组（不按内容类型分）
③ 按章节拆 references  → references/01-main-concept.md
                         references/02-detailed-flow.md
                         references/XX-pitfalls.md
④ 写薄 SKILL.md        → ~30-50 行：描述 + 触发条件 + 速记 + 引用表
⑤ 检查引用             → 其他 skill 有没有指向旧章节号？
```

- **自包含** — 每个功能文件在该场景下能独立提供价值，不依赖 SKILL.md 其他部分
- **有交叉引用** — 指向其他文件，不重复内容
- **保留翻车记录** — 每个文件末尾保留该功能域的失败案例
- **清理冗余** — 拆分中发现的重复内容直接删，不保留归档

## 优先级分组（GROUP 分类法）

不要抓到哪个 skill 就减哪个。按优先级排序：

| GROUP | 类型 | 特征 | 优先级 | 示例 |
|:------|:-----|:-----|:-------|:-----|
| 🟢 A | 已做薄 | ≤50 行，不动 | 跳过 | documents, diary-writer |
| 🟡 B | 方法论 | 纯文字步骤说明，无脚本依赖 | **最高** | TDD, spike, debug |
| 🔴 C | 工具型 | 有 CLI/脚本但说明太多 | **高** | github-*, bili-archive |
| 🔵 D | 资料库 | 内容/参考类，不需要大减 | 低 | short-stories, 词库 |
| 🟣 E | 合理 | 厚度结构 ok | 低 | hermes-agent, cron-ops |

按 GROUP 顺序下手。B 类最安全，砍了不影响功能，节省 60-90%。

## 铁律

- **禁止创建 monolithic references/full-reference.md** — 一个功能一个文件，不要全部 dump 进去。这是「换汤不换药」的反模式。
- **每个 skill 至少一个 references/ 文件** — 0 个文件说明 SKILL.md 还不够薄。
- **section 命名有意义** — 不叫 `ref1.md`，叫 `01-phase-1-root-cause.md`。
- **说明 md 也能拆** — 已经写好的 references 不算内容；SKILL.md 里内嵌的详细说明（流程/长规则/踩坑/模板/代码示例）才是要拆的对象（2026-08-06 全库验证）。

## 引用表格式

SKILL.md 的引用表统一用这个格式：

```
| 你要查什么 | 打开 |
|:-----------|:-----|
| 核心概念 | `references/01-xxx.md` |
| 详细操作 | `references/02-yyy.md` |
| 踩坑记录 | `references/03-pitfalls.md` |
```

## 拆薄工具 · `scripts/skill_thin.py`（2026-09-22 立）

> 用途：**spec 驱动**地把厚 SKILL.md 拆薄——规矩留、案例搬，搬运逐字不丢。
> 用法：写 `spec.json` → `python3 scripts/skill_thin.py spec.json`（dry-run 出报告）→ 加 `--write` 落盘。
> 触发：某个 SKILL.md 超 30KB / 超 200 行；或要按同一模子一次拆好几个。

spec 字段：`skill_dir` / `ref_meta`（新 ref 的题头）／`section_moves`（整节搬：`verbatim` 或 `auto_index`）／`moves`（逐条搬：`match` 前缀 + `keep` 一行）／`append`（拆分记录块，`#SIZE#` 自动填拆后体积）。

**三条内建保证**

1. **逐条守恒校验**——每条搬走的原文取其「最长差异窗口」当指纹：必须不在新 SKILL.md、必须在 ref 里；每条 keep 行必须出现在正文。
2. **整篇守恒复核**（拆完自己再跑一遍）——原文每行（>40 字）必须出现在 `新 SKILL.md ∪ 新 refs` 里，缺一即报。
3. 落盘前先备份：`cp SKILL.md cache/SKILL.md.<skill>.bak-$(date +%Y%m%d-%H%M)`。

**三个坑（实测）**

- **指纹别用固定切片**：keep 行常保留 ref 路径指针，固定切片（如 `25:50`）会假报「残留」；用「原文里最长的、不在 keep 里的 12 字窗口」才准。
- **auto_index 防「冒号太靠前」**：`- 平台：…` 会被第一个全角冒号切成孤零零的 `- 平台`——规则＝冒号位置 <30 不切，无冒号的超长条目用 `index_overrides` 手给一句话。
- **节替换后补空行**：repl 末尾不补空行，会把下一个 `## ` 顶上来粘在指针行后面。
- **ref 头 frontmatter 的 skill 名别硬编码**（2026-09-22 修）：早先写死「随 war-criminal-archive 主 skill」，拆别的 skill 时四个子代理都得自己 sed 一遍——现在由 `skill_dir` 推导。
- **两种 ref 落法**（2026-09-22 加）：`ref_meta.<ref>.append=true` ＝**并入既有 ref**（原样保留 + 追加一节带 marker），用在「一个主题一档、不重复存两遍」的场合（例：`delegation-and-verification` §七 并入既有 `landing-review-findings.md`）；`moves[].keep=""` ＝该条整体搬走、正文不留占位（别留一堆空行）。

**换轴经验**（2026-09-22，`delegation-and-verification` 53.4KB → 15.8KB）：**先看每个「肥」在哪**——若条目已是一条判据一行、肥在**条目数**而非单条长度，那就不是「案例搬」，该**按场景切**（§一 任务书 / §三 验收 / §五 检索型 / §六 评审型 / §七 落地 / §八 外部评审 各成一档，高频的 §二 并行、§四 坑 原样留）。判据：随机抽 5 条，能砍掉一半字数的是「案例型」（搬），砍不动的是「判据型」（按场景整节搬）。

**实测**（`war-criminal-archive`，2026-09-22）：SKILL.md 59.4KB／157 行 → **20.6KB／168 行（-65%）**，搬出 65 条 50.4KB 进 4 个新 ref（合计 55.1KB，多出的是题头）；守恒校验 0 丢失、0 残留。

### spec 的第三种定位：`line_moves`（2026-09-25 加）

```json
{"line_moves": [{"start": 37, "end": 52, "ref": "references/<新档>.md",
                 "label": "0", "title": "序列维 · 病根 · 解药 · 两个坑",
                 "keep": "0. **先把「量什么」定对…** → `references/<新档>.md`"}]}
```

- **坐标基于原文件、1-based、内部倒序执行**（多处搬动不会互相挪位）。
- 适用：**顶层条目行留一句摘要、其下整段缩进展开搬走**的拆法（厚 SKILL 里「编号条目 + 子条目」结构最典型）。
- 三种定位分工：`section_moves` 管整节（`##`／`###` 标题定位）、`moves` 管单条（行首前缀唯一匹配）、`line_moves` 管行段。

### 四个修复（实测撞出来的）

1. **整节搬会漏标题**：早先 `section_moves` 只把 body 搬进 ref，`## 标题` 行被 keep_text 替换掉、**ref 里没标题**——一次 17 节的拆分就丢 17 个标题（复核时只有超 40 字的长标题露头）。现在标题随内容一起进 ref。**判据：ref 里 `## ` 计数 == 搬走的节数。**
2. **`###` 子节会被 `##` 兄弟节吞掉**：`section_end` 原只认 `## `，搬 `### 6b.` 会一路吞到父节末尾。现在按「同级或更高级标题」定位。搬子节前先看 ref 体积是否符合预期。
3. **格式行假残留**：` ```bash `、`|:--|:--|:--|` 这类短行当指纹必然与保留节撞车，报一堆「残留」。现在 <25 字（probe）／<30 字（detail）不做指纹。
4. **代码围栏里的 `#` 不是标题**（2026-09-28 撞出）：`section_end` 原先见 `#` 开头的行就判同级标题——撞上 ` ```bash ` 里的 `# ── 路线 A` 会把节尾判在那儿，实测 `tieba-extractor`「长帖全量抓取」**62 行的节只搬出 7 行／133 字符**。⚠️ 逐条守恒校验**查不出这个**（搬走的确实在 ref 里），只有干跑报告里的 ref 体积露头——**落盘前先看三个 ref 的体积合不合常识**。现在按 ``` 围栏开关跳过代码块内容。

### 收尾四件事（缺一个就可能欠新账）

| 步骤 | 做法 |
|:--|:--|
| **整篇守恒复核** | 原文件每行 >25 字必须出现在「新 SKILL ∪ 全部 refs」——工具的逐条校验覆盖不到标题行与短行，这一步才是兜底 |
| **相对指涉复核** | 搬走后「见上／见下／上一节／本节」这类**指向文档结构**的指涉会失锚，尤其所指的那节也一起搬了（实测四件里撞到 4 处：SKILL 说「见下两节」、ref 说「见上一节」——对象早搬去别的文件）。逐处核它指的是不是还在同一文件，不在就写明确路径。**判据：看它说的是文档还是被写的东西**——「上一节埋的刻字」指稿子的节，别误伤 |
| **mdcheck 前后对比** | 整理前先 `git archive HEAD skills/<name> \| tar -x -C <临时目录>` 出基线跑一遍，整理后**同数或更低**才算没欠账（实测两处新账全出在「拆分记录里写裸文件名」「占位名带反引号」） |
| **压连续空行** | `keep_text=""` 的节会在原位留空行——落盘后 `re.sub(r'\n{3,}', '\n\n', text)` |

**写「拆分记录」时的引用**：提到 ref 要带 `references/` 前缀写全路径；**裸文件名会被 mdcheck 当断链**，`NN-` 这类泛化占位名也别带反引号。同理，文档里给**示例路径**时用 `<…>` 占位（占位符在脚本内置排除表里），别写一个看起来像真文件的名字。

### 四件连拆实测（2026-09-25）

| skill | 前 | 后 | 降幅 | 拆法 |
|:--|--:|--:|--:|:--|
| prose-quality-metrics | 60.6KB | 19.1KB | −68% | 铁律节「判据留、缩进展开搬」（line_moves + 并入既有场景档） |
| md-link-maintenance | 28.9KB | 6.5KB | −77% | 细粒度场景整节归四档（section_moves，17 节） |
| draft-archaeology | 36.3KB | 9.9KB | −73% | `###` 工序子节按主题归位（3 新档 + 4 并入） |
| dev-workflow | 36.5KB | 6.8KB | −81% | 32 条原则逐条搬（moves，按场景四档） |

**合计 162.3KB → 42.3KB（−74%）**，全部 0 丢失／0 残留；四件的 mdcheck 都不高于各自基线。

## Prompt 做减法 · 独立场景

> 2026-08-02 追加。减法哲学不只在技能库维度，**给 LLM 的 prompt 同样要做减法**。

### 核心区别

| 维度 | 技能库做减法 | Prompt 做减法 |
|:-----|:------------|:--------------|
| 砍什么 | 章节/文件/冗余说明 | **只砍冗余说明** |
| 不砍什么 | 功能拆分进 references | **功能约束/结构维度一个不删** |
| 目标 | SKILL.md 变薄入口 | prompt 变短但语义密度更高 |

**铁律：Prompt 做减法 = 移除冗余说明，不是砍功能维度。** 该保留的（结构、约束、边界）一个不能少，否则模型行为会变。

### 实操案例：vision 提示词 v3 精简（1093→481 字符）

**砍掉的冗余：**
1. **开头与边界重复** — 「允许轻微氛围推断，但禁止补充画面外信息」里的「禁止画面外」和边界 1（不猜身份）/4（不补剧情）重复 → 删开头
2. **边界合并** — 边界 1（身份出处）和 2（对比联想）本质都是「不联想」→ 合并成一句
3. **长句压缩** — 长句 → 压成「动词+宾语」短句
4. **示例压缩** — 括号里解释性示例 → 压成关键词枚举

**保留的全部功能：** 4 维结构、多人按编号分述、服装细节、握持方式、光影、边界 5 条核心约束——一个不少。

### Prompt 做减法的检查清单

- [ ] 开头声明与正文边界是否重复？（重复就删开头）
- [ ] 两条边界/约束是否本质同一条？（同就合并）
- [ ] 长句是否能用「动词+宾语」短句表达？
- [ ] 括号示例是「约束枚举」还是「解释性说明」？（前者保留，后者压缩）
- [ ] 砍完是否所有功能关键词还在？（结构/约束/边界一个不能丢）

### 附：reference 内部重组也要守恒校验（2026-09-25 实测）

场景：不是拆 SKILL.md，而是把一份胖 reference（24.8KB）重组成「主档 + 附档」。
**第一次拆漏掉一整节**（CLI/工具节没被任何一档收进去），还覆盖掉了上一轮刚补的两处内容（英文枚举、字段行）——
两处都是靠事后校验才抓回来。行数少了八成，看起来「减得不错」，实际掉了东西。

**三步，别省：**

1. **先切分缓存**：`re.split(r'\n(?=## )', txt)` → 节字典落 JSON，再按新顺序组装。
   **别凭记忆重写**——重写必丢（内容以原文段落为单位搬运，只做标题与少量替换）。
2. **组装后做两类守恒核对**：
   - **节归属表**：旧节清单 × 新文件归属，出现「未纳入任何一档」的节＝漏搬。
     （只看行数/体积看不出来——一节 30 行在 365 行里不显眼。）
   - **集合比对**：两边各取①标识符 `[a-z][a-z_0-9]{4,}` ②3-5 位数字 ③`:\d{3,5}` 行号引用，
     比对新出现 / 消失项；消失项**逐条判定**是有意删还是漏搬。
3. **未提交的补丁先留住**：以 `git show HEAD:<file>` 当基线重组时，工作区里没提交的修补会一起丢。
   重组前先 commit，或把补丁内容单独记下来回放。

判据：**行数少 ≠ 减对了**；节清单与三个集合都对得上，才算减成。
